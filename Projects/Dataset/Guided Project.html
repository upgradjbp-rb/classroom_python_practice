Q12: Year-over-Year (YoY) Sales Growth Rate

Measuring macro platform expansion using LAG()

The Commercial Problem

Investors require verified Year-over-Year growth percentages to gauge whether Olist's marketplace adoption is accelerating or saturating.

-- Advanced Query 3: WITH annual_revenue AS ( SELECT YEAR(o.order_purchase_timestamp) AS sales_year, ROUND(SUM(py.payment_value), 2) AS total_sales FROM orders o JOIN payments py ON o.order_id = py.order_id GROUP BY YEAR(o.order_purchase_timestamp) ) SELECT sales_year, total_sales, LAG(total_sales) OVER (ORDER BY sales_year ASC) AS previous_year_sales, total_sales - LAG(total_sales) OVER (ORDER BY sales_year ASC) AS yoy_growth_inr, ROUND(100.0 * (total_sales - LAG(total_sales) OVER (ORDER BY sales_year ASC)) / NULLIF(LAG(total_sales) OVER (ORDER BY sales_year ASC), 0), 2) AS yoy_growth_pct FROM annual_revenue;

Q13: Customer Retention Rate Analysis

Calculating the percentage of customers who made more than one purchase

The Commercial Problem

Acquiring customers is expensive. Retention rate measures sustainable loyalty: what percentage of total registered customers made 2 or more purchases?

-- Advanced Query 4: WITH repeat_buyers AS ( SELECT customer_id, COUNT(order_id) AS order_count FROM orders GROUP BY customer_id HAVING COUNT(order_id) > 1 ) SELECT COUNT(*) AS repeat_customer_count, (SELECT COUNT(DISTINCT customer_id) FROM customers) AS total_customers, ROUND(100.0 * COUNT(*) / (SELECT COUNT(DISTINCT customer_id) FROM customers), 2) AS customer_retention_rate_pct FROM repeat_buyers;

Query Refactoring Slide 37 / 50

Production Refactoring: Fixing Subqueries & Joins

Optimizing queries for high-throughput enterprise environments

Inefficient Unnested Join Pattern

Joining payments on order_items without grouping can duplicate payment values if an order contains 5 items!

Production-Grade Refactored Pattern

Join payments directly to orders at the order-header grain to ensure accurate revenue calculations without duplication.

-- Safe grain alignment: SELECT o.order_id, py.payment_value FROM orders o JOIN payments py ON o.order_id = py.order_id;
SARGability in Practice Slide 38 / 50

Refactoring Date Filters for High-Speed Index Use

Replacing YEAR() with SARGable date ranges in 2017/2018 queries

Slow Non-SARGable Pattern

WHERE YEAR(order_purchase_timestamp) = 2017;

Forces full table scan across 100,000+ rows!

Optimized SARGable Range

WHERE order_purchase_timestamp >= '2017-01-01' AND order_purchase_timestamp < '2018-01-01';

Leverages B-Tree index range scans directly!

Packaging the Project: v_master_ecommerce_kpis

Creating a consolidated reporting view for dashboard tools

CREATE OR REPLACE VIEW v_master_ecommerce_kpis AS SELECT o.order_id, c.customer_id, c.customer_city, c.customer_state, o.order_purchase_timestamp, YEAR(o.order_purchase_timestamp) AS purchase_year, MONTH(o.order_purchase_timestamp) AS purchase_month, p.product_category, oi.seller_id, py.payment_type, py.payment_installments, py.payment_value FROM orders o JOIN customers c ON o.customer_id = c.customer_id JOIN order_items oi ON o.order_id = oi.order_id JOIN products p ON oi.product_id = p.product_id JOIN payments py ON o.order_id = py.order_id;

Automation: sp_generate_annual_sales_summary()

Automating annual revenue reporting via stored procedures

DELIMITER $$ CREATE PROCEDURE sp_generate_annual_sales_summary(IN p_year INT) BEGIN SELECT MONTH(o.order_purchase_timestamp) AS calendar_month, COUNT(DISTINCT o.order_id) AS total_orders, ROUND(SUM(py.payment_value), 2) AS total_sales FROM orders o JOIN payments py ON o.order_id = py.order_id WHERE YEAR(o.order_purchase_timestamp) = p_year GROUP BY MONTH(o.order_purchase_timestamp) ORDER BY calendar_month ASC; END $$ DELIMITER ;

Technical Interview Prep Slide 45 / 50

Defending the Project in Technical Interviews

Anticipating interview questions and delivering structured answers

Q: "How did you avoid payment value duplication when joining items and payments?"

Answer: "An order can contain multiple items. Joining payments directly to order_items without aggregation can multiply payments. I aligned grains by joining payments to orders, or aggregating items before joining."

Q: "Why use DENSE_RANK over RANK for annual top spenders?"

Answer: "DENSE_RANK() ensures that if two customers tie for 2nd place, the next customer receives 3rd rank, ensuring clean Top-3 filtering without skipped positions."

Pre-Flight Review Slide 47 / 50

The Analyst's Query Audit Checklist

Five checks before delivering SQL outputs to management

  • 1. Grain Alignment: Did I confirm whether my output is at the customer, order, or item grain?
  • 2. SARGable Conditions: Did I avoid wrapping indexed columns in functions like YEAR() in high-volume tables?
  • 3. NULL Safety in Division: Did I wrap denominators in NULLIF(..., 0) when calculating percentages?
  • 4. Explicit Column Naming: Are all columns in multi-table queries prefixed with table aliases?
  • 5. Deterministic Tie-Breaking: Did I provide a secondary sort column in window functions to ensure consistent rankings?
